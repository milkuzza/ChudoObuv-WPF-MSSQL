# Приведение данных к третьей нормальной форме

Обработаны все пять файлов с пометкой `import`, предоставленных в приложении 2. Созданы согласованные Excel, CSV, Microsoft SQL Server и SQL-скрипт с одним набором идентификаторов.

## Шаги нормализации

**Первая нормальная форма.** В каждой ячейке хранится одно значение атрибута; нет столбцов «Товар 1», «Товар 2» или списков размеров. Одна строка `stock_items` описывает одну модель одного размера. Одна строка `order_items` описывает одну товарную позицию в одном заказе. Свободные тексты описания и состава используются приложением как единый текст, поэтому не разбиваются на отдельные слова или материалы.

**Вторая нормальная форма.** Из повторяющихся строк заказов выделены заголовки `orders`. Дата и клиент зависят от номера заказа; количество и фактическая цена продажи относятся к конкретной строке. Свойства модели не хранятся в сочетаниях модели и размера. Естественные составные ключи закреплены `UNIQUE`, даже при наличии суррогатного первичного ключа.

**Третья нормальная форма.** Название роли хранится только в `roles`, названия категорий, типов и производства — в соответствующих справочниках. В `users` записан `role_id`, в `products` — идентификаторы справочников. ФИО клиента не дублируется в заказах, название и производство модели не дублируются в строках заказа. Нетривиальные зависимости неключевых атрибутов от других неключевых атрибутов исключены; атрибуты каждого отношения зависят от его кандидатного ключа.

Тип обуви (`subcategories`: сапоги, туфли, кроссовки и т. д.) и категория аудитории (`categories`: детская, женская, мужская обувь) независимы. Один тип встречается в нескольких категориях. Поэтому `subcategory_id` не определяет `category_id`; хранение обеих ссылок в `products` не создаёт транзитивную зависимость.

`unit_price_kopecks` в строке заказа — историческая цена сделки, а не копия текущего `price_kopecks` модели. Она может отличаться из-за скидки и последующих изменений каталога. Итог заказа не хранится в таблице: его вычисляет представление `order_totals` через сумму `quantity × unit_price_kopecks`.

Размерный ряд модели получается из всех её `stock_items`, доступные размеры — из строк с `available_quantity > 0`. Отдельные текстовые списки размеров не создаются.

## Правила подготовки данных

1. Удалены крайние и повторные пробелы, неразрывный пробел заменён обычным. В заголовке пользователей исправлено исходное «Отчетсво» на поле `middle_name`.
2. Размеры, записанные в исходном Excel строками (`36.5`, `37.5` и др.), преобразованы в числа; все 35 исходных значений сохранены.
3. Исходные рубли переведены в целые копейки через десятичную арифметику. Числа не преобразованы в строки с символом валюты.
4. ФИО из заказа сопоставлено с полной комбинацией фамилии, имени и отчества в `Users_import.xlsx`. Все клиенты найдены; новые вымышленные пользователи не добавлялись.
5. Модель сопоставлялась по очищенным наименованию и производству; категория заказа сверялась с каталогом. Связь размера определялась по числовому значению.
6. Для каждого номера заказа проверено совпадение даты и клиента во всех исходных строках.
7. Три строки остатков и одна строка заказа с названием «Черные туфли в классическом стиле» и производством «Барбари» связаны с полной моделью «Черные туфли в классическом стиле — база для деловых образов» (`product_id = 26`). Других неоднозначных соответствий не обнаружено.
8. В свободном описании некоторых исходных моделей упоминается производство, отличающееся от структурированного столбца «Производство». Текст описания сохранён как предоставлен; идентификатор производства определён по структурированному столбцу. Эти расхождения требуют уточнения владельца исходных данных, но не препятствуют сохранению связей.
9. Остатки импортированы как уже доступное количество. Исторические заказы повторно не вычитались. При отмене заказа приложение возвращает его количество в доступный остаток.

## Контрольные суммы

| Доступных пар | 1 274 |
| Заказов | 10 |
| Строк заказов | 30 |
| Пар в исторических заказах | 36 |
| Сумма исторических заказов | 341 770,00 руб. |

Проверены все FK, уникальность ключей, отсутствие потерянных исходных строк и загрузка SQL-скрипта в пустую базу Microsoft SQL Server. Ограничения PK, FK, UNIQUE и CHECK действуют в MSSQL. Денежные значения представлены bigint (копейки), размеры — decimal(4,1), даты — date. Все FK используют NO ACTION, кроме удаления строк заказа каскадом при удалении заголовка.

Excel не является СУБД и не обеспечивает ограничения внешних ключей при ручном редактировании. Третья нормальная форма здесь отражена структурой отдельных листов. Рабочая база Microsoft SQL Server обеспечивает PK, FK, `UNIQUE`, `NOT NULL`, `CHECK` и транзакции.
